# Agent Note: 取消固定观看人数上限

Status: implemented

## Problem

用户明确要求不限制观看人数。原来的单观看者标记和八个 WebSocket 上限会拒绝正常的第二个页面或后续连接。
本决定部分取代[首版媒体边界](../architecture/2026-11-17-python-gstreamer.md)中的单观看者限制，保留原有 Python、GStreamer、鉴权和媒体传输选择。

## Decision

信令服务不设置固定观看人数或 WebSocket 总数上限。每个鉴权通过的观看者继续使用独立媒体会话，不共享 SDP、ICE、事件队列或管线清理状态。
一个观看者断开或发生错误只清理自己的会话，服务关闭时清理全部活动会话。Origin 校验、令牌比较、鉴权超时和消息大小限制保持不变。
页面明确说明多人观看受板端资源和带宽约束，不把取消业务上限表述为无限容量。
[SSRC 接入与原生会话释放修复](../bug-fix/2026-11-18-rtsp-session-lifetime.md)保留每个观看者独立管线和清理责任。

## Alternatives considered

- 保留单观看者限制可以约束首版资源消耗，但会阻止用户要求的同时观看，因此取消。
- 共享取流和编码可以减少摄像头连接和硬件编码消耗；当前需求是取消固定人数限制，现有每会话独立管线已能并行播放，因此本轮不引入共享源和分发重构。若实际负载或摄像头会话上限成为问题，再以测量结果决定共享方案。

## Consequences

九个替身媒体会话的单测验证准入不受旧上限影响、单会话清理隔离和全部会话关闭，不代表九路真实视频容量。
板端实测两个 Cursor Chromium 页面同时解码 640x360 测试视频，采样分别为 790 帧和 214 帧；断开第一个页面后，第二个页面继续增长到 676 帧。
每增加观看者会增加上行和原生管线资源；测试源与 H.265 转码会增加编码会话，RTSP 模式还会增加摄像头取流连接。未验证高并发容量或摄像头最大连接数。
真实摄像头仍需要已验证的 RTSP URL、摄像头凭据和可达网络。测试彩条是实时合成源，不是实际场景，也不是图像损坏。
