# Agent Note: 一次连接后的播放器恢复

Status: implemented

## Problem

用户要求直播只点一次 Connect，不应在每次断线后手动连接。
原播放器在 WebSocket、WebRTC 或媒体错误时直接停止；真实摄像头还出现过连接保持但画面停在第 13 帧的情况。
旧 video.play() 的异步拒绝也会在断开后把状态误改成已连接。

## Decision

播放器区分持续观看意图和单次媒体会话。Connect 开启观看意图，异常只关闭旧会话，并在退避后创建新的鉴权 WebSocket/WebRTC 会话。
重试间隔依次为 1、2、4、8、16、30 秒，上限 30 秒；画面持续推进至少 10 秒才恢复最短间隔，不因收到单帧或连接成功就重置。
每两秒检查视频帧计数，接口不可用时检查播放时间；连接状态正常但约 15 秒画面不再推进时重建会话。
用户主动暂停和浏览器禁止自动播放不触发停帧重连，用户恢复播放后重新监测。
Disconnect 和离开页面立即取消当前会话及等待中的重试。访问令牌错误终止自动重试，等待用户修正后再点 Connect。
旧会话的异步回调必须先核对会话身份，防止错误状态覆盖和重复恢复。

服务端仍清理失败会话；恢复由浏览器创建新会话，不改变鉴权、信令格式、RTP 分包、编码、线程或主机网络。
本决定补充[媒体边界](../architecture/2026-11-17-python-gstreamer.md)，不影响[独立多观看者会话](2026-11-17-multiple-viewers.md)。

## Alternatives considered

- 保留手动 Connect 可以避免自动重试，但不满足用户持续观看需求，因此仅对主动停止和访问令牌错误保留人工启动。
- 仅在 WebSocket 关闭后重连实现更少，但无法处理已复现的连接保持、画面不再推进，因此同时检查视频进度。
- 固定短间隔重试可以更快恢复，但持续故障时会重复创建摄像头和硬件会话，因此使用有上限的退避，并等待真实画面推进后再重置。

## Consequences

断线后无需重复点击即可尝试恢复，主动停止不再被重试覆盖；代价是故障期间仍定期建立会话，且自动恢复不能代替停帧根因修复。
八项无额外 npm 依赖的 Node 测试验证退避去重、媒体错误、令牌错误、主动停止、停帧、暂停、自动播放阻止、过期回调和连接超时。最初七项中五项在旧播放器失败。
五分钟持续播放检查使用模拟时钟和视频计数，不代表真实摄像头长期验收。原有 16 项 Python 测试、Ruff 和 JavaScript 语法检查通过。
板子 SSH 目前超时，代码仅在本地实现，尚未上传，也未验证真实摄像头自动恢复或定位其停帧根因。
回滚点和后续静态文件部署步骤见[部署说明](../../../deployment.md#player-recovery-local-change-not-yet-deployed)。
