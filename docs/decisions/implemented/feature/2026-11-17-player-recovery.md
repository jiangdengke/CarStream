# Agent Note: 一次连接后的播放器恢复

Status: implemented

## Problem

用户要求直播只点一次 Connect，不应在每次断线后手动连接。
原播放器在 WebSocket、WebRTC 或媒体错误时直接停止；真实摄像头还出现过连接保持但画面停在第 13 帧的情况。
旧 video.play() 的异步拒绝也会在断开后把状态误改成已连接。

## Decision

播放器区分持续观看意图和单次媒体会话。Connect 开启观看意图，异常只关闭旧会话，并在退避后创建新的鉴权 WebSocket/WebRTC 会话。
重试间隔依次为 1、2、4、8、16、30 秒，上限 30 秒；画面持续推进至少 10 秒才恢复最短间隔，不因收到单帧或连接成功就重置。
优先用 requestVideoFrameCallback 统计当前会话实际呈现的帧，每两秒检查进度；同时读取当前视频 inbound-rtp 的 framesDecoded，交叉判断是否仍在解码。呈现进度和解码进度均约 15 秒不再增长时重建会话。Firefox 的实时 MediaStream 播放质量计数可能始终为零，Cursor 也可抑制呈现回调但继续解码，不能因接口存在就认定其计数可靠。
不支持呈现帧回调时使用大于零的播放质量计数，否则回退到播放时间。时间回退在旧浏览器不能严格证明新帧到达；现代浏览器不能用持续走动的播放时钟掩盖真实停帧。
解码检查只使用实际解码的视频帧，不能用收包、字节或播放时钟增长代替。统计读取失败时保留原有呈现进度检测；同一会话的异步读取不重叠，完成后重新核对当前会话和连接状态，不能影响替换会话。解码推进不能证明屏幕合成正常，本机制避免误重连，不承诺检测仅发生在显示端的黑屏。
断开时取消当前会话的呈现帧回调；晚到回调先检查会话身份，不得更新或重建后续会话的监测器。
用户主动暂停和浏览器禁止自动播放不触发停帧重连，用户恢复播放后重新监测。
Disconnect 和离开页面立即取消当前会话及等待中的重试。访问令牌错误终止自动重试，等待用户修正后再点 Connect。
旧会话的异步回调必须先核对会话身份，防止错误状态覆盖和重复恢复。

页面不依赖界面测试参数选择版本。载入时仅清除遗留的 `ui` 参数，以 history.replaceState 更新当前地址，保留其他参数、片段和历史状态。不重载页面、不新增历史记录或自动连接，避免为清理地址再次打断观看；无需重启服务或修改鉴权。

服务端仍清理失败会话；恢复由浏览器创建新会话，不改变鉴权、信令格式、RTP 分包、编码、线程或主机网络。
本决定补充[媒体边界](../architecture/2026-11-17-python-gstreamer.md)，不影响[独立多观看者会话](2026-11-17-multiple-viewers.md)。
[SSRC 接入与原生会话释放](../bug-fix/2026-11-18-rtsp-session-lifetime.md)处理服务端已复现的缺陷，不能用客户端自动恢复替代。

## Alternatives considered

- 通过服务端重定向或 location 跳转清理测试地址会增加请求或重载，还需要修改服务；仅替换当前历史地址足以移除遗留标记，因此不采用重定向。
- 保留手动 Connect 可以避免自动重试，但不满足用户持续观看需求，因此仅对主动停止和访问令牌错误保留人工启动。
- 仅在 WebSocket 关闭后重连实现更少，但无法处理已复现的连接保持、画面不再推进，因此同时检查视频进度。
- 固定短间隔重试可以更快恢复，但持续故障时会重复创建摄像头和硬件会话，因此使用有上限的退避，并等待真实画面推进后再重置。
- 只依赖呈现回调能发现显示停滞，但 Cursor 已复现回调停止、解码继续并被播放器误断开的情况，因此增加解码帧交叉检查。仅延长停帧阈值会推迟真正故障恢复，也不能消除这种误判；使用收包字节或播放时钟代替又会掩盖解码停滞，因此不采用。

## Consequences

中文界面及地址清理后共有十五项 Node 测试通过。新增地址回归覆盖旧测试链接变为根地址、干净地址不改写、其他参数与片段保留，以及清理过程不自动连接、后续令牌提交不变；该回归在地址清理前失败、清理后通过。
断线后无需重复点击即可尝试恢复，主动停止不再被重试覆盖；代价是故障期间仍定期建立会话，且自动恢复不能代替停帧根因修复。
十三项无额外 npm 依赖的 Node 测试验证退避去重、媒体错误、令牌错误、主动停止、停帧、暂停、自动播放阻止、过期回调和连接超时。其中两项覆盖实时质量计数始终为零、呈现帧持续推进、真正停帧、回调清理与旧浏览器时间回退；这两项在 Firefox 修复前失败、修复后通过。后续三项覆盖呈现回调受抑制但持续解码、收包和播放时间继续时的真实解码停滞、统计读取失败、读取去重和过期结果隔离；其中两项在解码检查修复前失败，修复后十三项全部通过。最初七项中五项在初版播放器失败。
五分钟持续播放检查使用模拟时钟和视频计数，不代表真实摄像头长期验收。原有 16 项 Python 测试、Ruff 和 JavaScript 语法检查通过。
板子 SSH 恢复后，仅将验证过的 player.js 备份并原子替换到当前发布目录；服务进程未重启，鉴权、媒体和主机网络保持不变。
浏览器仅点一次 Connect，主动关闭该测试会话的 WebSocket 后，页面等待一秒重试并约两秒恢复连接；真实摄像头解码帧数在恢复后从 193 增至 446。
后续真实画面再次停滞，页面按 1、2、4、8、16 秒退避自动重试，但新建 WebRTC 连接未恢复持续播放；已主动 Disconnect 停止诊断会话。
这验证信令中断后的真实恢复和停帧检测，不代表持续直播通过。停帧根因仍未定位，停帧前统计为丢包 267、收包 11532；不能据此断定具体故障环节。
部署校验、备份位置和静态文件回滚命令见[部署说明](../../../deployment.md#player-recovery-deployed)。
替换板 Firefox 的专项检查确认实际呈现帧数从 369 增至 1458，播放时间从 19.725 秒增至 77.543 秒，而旧播放质量计数始终为零。新版播放器以真实呈现回调保持连接；只替换静态文件并刷新浏览器，不重启 Python 或改变同源、编码、云端配置。该检查独立于同轮出现的 rtspsrc resource 9/7 错误，不能宣称摄像头连接与长期播放问题全部修复。专项部署与回滚见[Firefox 兼容性记录](../../../deployment.md#firefox-presented-frame-progress-repair-2026-11-19)。
后续公网 Cursor 五分钟只读观察记录八次停帧误判：一个会话的解码帧从 30 增至 328、取样亮度正常，但呈现计数始终为零；旧播放器仍主动清空媒体并逐步退避至 30 秒。解码交叉检查只替换静态播放器，保留运行进程、令牌、原分辨率及媒体配置。该复现证明一类黑屏由播放器主动断开造成，不证明其他设备的黑屏、历史 RTSP 错误或显示合成问题都已解决。部署与验证边界见[Cursor 黑屏修复记录](../../../deployment.md#cursor-false-stall-blackout-repair-2026-11-19)。
