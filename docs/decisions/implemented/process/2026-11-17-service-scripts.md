# Agent Note: 手动服务启停使用两个脚本

Status: implemented

## Problem

README 原来要求手动加载环境、后台启动、记录 PID，再人工核对并停止。
用户要求改为启动和停止两个 sh 脚本，减少重复操作，但不能误停其他 Python 进程或覆盖当前服务的 PID。

## Decision

提供根目录可执行的 ./start.sh 和 ./stop.sh，只面向 Ubuntu/Linux，以脚本位置确定当前发布目录。
启动自动加载可信 .env，通过当前虚拟环境校验配置，检查端口，再后台运行同一发布的 Python 应用。
每次实际启动把标准输出和错误写到 log/carstream-<UTC 启动时间>.log，时间包含纳秒，启动结果打印实际日志路径。每次重启单独留档，重复调用已运行服务不新建日志，不增加跨天轮转或自动清理。
启动成功以新进程拥有配置端口的监听套接字为准；已有匹配进程时不重复启动，端口占用、非法 PID 或无关进程直接报错。
停止不加载 .env，先核对正整数 PID、完整命令和工作目录，再发送 SIGTERM。最多等约 30 秒，不升级为强制结束。
启动等待约 10 秒仍未监听时保留活进程的 PID 并报错；停止超时也保留 PID，便于检查，不能当作成功。
server.lock 只串行化同一发布的启停操作，后台进程不继承锁。PID 和日志权限为 0600，log 目录权限为 0700；运行文件忽略提交，只跟踪空目录占位。
同步白名单包含根目录脚本并保留可执行权限，不同步运行日志，板端缺失的 log 目录由启动脚本创建。旧 server.log 不删除、不迁移。
脚本不安装依赖、不配置 systemd 或开机自启、不管理 SSH 转发，也不修改媒体、鉴权、线程或主机网络。
本决定补充[媒体与部署边界](../architecture/2026-11-17-python-gstreamer.md)，不改变同步脚本只上传、不启动服务的约束。
[公网隧道](../architecture/2026-11-18-public-access.md)另行使用用户级 systemd，仅管理反向 SSH；不取代本决定的 Python 应用手动生命周期。

## Alternatives considered

- 保留 README 手动命令不增加维护文件，但每次都要重复加载环境、记录和核对进程，不能满足用户要求的直接启停入口。
- systemd 更适合长期托管、崩溃恢复和开机启动，但当前只要求两个手动脚本，安装系统服务会扩大部署与权限范围，因此不采用。

## Consequences

收益是服务启停入口统一，并保留拒绝重复启动和误停的检查。代价是依赖 Linux 的 /proc、ss 和 flock，且只管理记录在当前发布 server.pid 中、使用约定命令启动的进程。
现有板端后台进程使用相同的命令和 PID 文件约定；前台手动启动仍需原终端 Ctrl+C，脚本不会扫描全机 Python 进程。
八项 Linux 集成测试使用独立临时发布和标准库 HTTP 模拟服务，覆盖直接执行、背景启动、按启动时间分日志、重启不覆盖旧日志、重复调用、缺失环境时停止、非法与过期 PID、无关进程、占用端口、启动失败和操作锁。
当前根目录入口和时间日志版本通过本地语法与静态检查，八项更新后的 Linux 集成测试已在板端隔离目录通过；macOS 明确跳过这些检查。
按启动时间分文件让每次运行的日志独立保留，但不会限制单次长期运行的文件大小，也不会自动回收磁盘；使用方需关注占用。
脚本已部署到当前运行发布，公网配置切换时真实应用经 SIGTERM 停止并通过新入口启动，新日志按时间留档。媒体稳定性仍需独立验收，不能由启停成功推出。
部署边界与回滚见[启停说明](../../../deployment.md#startstop-scripts)。
