# Agent Note: 摄像头 SSRC 切换与原生会话释放

Status: implemented

## Problem

公网能出画但反复中断。板端隔离取流复现摄像头先后输出 SSRC 0、1、2；旧 pad-added 只接第一个视频 pad，后续 pad 未连接，rtspsrc 在数秒后报 not-linked 并终止管线。
另一个独立问题是原生信号闭包保留 Python 会话：关闭三个测试会话后，文件描述符从 7 增至 96，会话弱引用均存活。不能仅凭生产 TURN 连接数推断它就是全部停帧原因。

## Decision

每个 RTSP 会话在 depayloader 前使用原生 funnel，为匹配视频编码的每个动态 pad 分配独立输入，保留 caps 和 sticky events，再接原有 queue、解码、编码和 RTP 打包。
此路径针对实测同一摄像头视频的 SSRC 切换，不把不同摄像头或独立视频轨混为一路。音频继续不选择；编码不匹配继续报安全错误。

会话记录自己注册的原生信号 handler，关闭和构造失败均先停止管线，再断开 handler 并释放持有的原生元素引用。重复关闭无副作用，不手动 unref GI 对象。
错误只提取工厂名称、固定域类别和数字错误码，绝不转发原生 message/debug 中可能存在的凭据；应用日志附时间和已脱敏错误，便于关联断流。
保留[Python/GStreamer 媒体边界](../architecture/2026-11-17-python-gstreamer.md)、[独立多观看者](../feature/2026-11-17-multiple-viewers.md)和[浏览器自动恢复](../feature/2026-11-17-player-recovery.md)，不修改网络、摄像头设置或重试阈值。

## Alternatives considered

- 只靠浏览器重连无需改媒体接入，但同一摄像头每次都会再次输出未连接 pad，且回调泄漏会积累，因此不能代替修复。
- rtpfunnel 专门处理 RTP，但板端真实流试验立即报 not-negotiated；通用 funnel 保留摄像头输入 caps 后能够继续通过 SSRC 切换，因此采用后者。
- 只把管线设为 NULL 最简单，但原生信号闭包不由 Python 循环 GC 解开，弱引用和 FD 增长已经复现，因此显式管理 handler 生命周期。

## Consequences

收益是后续 SSRC 不再因未连接而终止取流，关闭会话不再保留原生回调；代价是多个输入仍依赖摄像头的连续码流语义，不能宣称支持任意多轨复用。
原生双 SSRC 回归在旧实现失败，接入 funnel 后通过；没有打开真实摄像头。构造失败、原生错误脱敏、重复关闭和原生弱引用终结检查通过。
十次测试会话均实际取得 TURN relay 候选再关闭，文件描述符在延迟释放完成后保持 17，pipeline 与 webrtcbin 的原生终结回调均触发。首次仅等待半秒的严格 FD 检查曾失败；额外十轮诊断确认一秒后描述符回到相同基线，没有放宽增长上限。
测试视频 WebRTC 回环解码至少十帧，最大 RTP 包 1200 字节。普通 Python 和 Node 测试不需要原生环境，原生回归按需单独执行。

隔离诊断曾在约 37-61 秒停住，停流时 RTSP TCP 接收队列仍有积压，原生取流任务暂停，下游均等待输入；关闭 RTCP 的对照同样失败，不据此修改生产 RTCP、缓冲或超时。
后续原参数探针持续推进 90 秒和 180 秒，后一轮编码 3600 帧且跨过 SSRC 切换，但诊断探针不能替代生产路径验收，也不能排除间歇故障。仅曾收到数据、进程未退出或退出码为零，均不能作为持续播放通过的依据。
两项修复已先后备份并部署到当前发布，未改摄像头、凭据、路由或云端现有服务；部署校验、日志和分层回滚见[稳定性记录](../../../deployment.md#rtsp-stability-repair)。
部署后的公网 300 秒目标试验未通过：强制 relay/relay，最后周期样本为第 163 秒、2352 个解码帧，随后 20 秒收不到新帧而失败。同期服务器出现 rtspsrc 读取错误和安全摘要的 ValueError，但缺少观看会话关联，不能把这些错误全部认定为该客户端的停帧原因。
隧道保持活动且重启次数为零，接收端报告丢包仍不能定位丢包环节；不据此猜测网络根因，也不追加未经验证的 RTCP、缓冲、码率或超时改动。
后续同一隔离观看会话的 300 秒观察窗口解码 5765 帧，但出现 6.61 秒帧间隔。卡顿时板端取流、MPP 编码和 RTP 打包继续推进，接收端报告丢包增加并随后自行恢复；这一次问题收窄到 RTP 打包之后，仍不能区分原生 WebRTC 发送、TURN/网络传输与接收解码恢复。
该会话信令走临时 SSH 转发，媒体仍经现有公网 TURN，未重启或替换生产服务；不能据此判定公网代理根因，也不能覆盖此前 RTSP 读取错误。诊断完成并清理临时监听后，下一项证据是同一会话的发送传输统计与接收进度；浏览器、流畅性和长期稳定性仍未验收。
