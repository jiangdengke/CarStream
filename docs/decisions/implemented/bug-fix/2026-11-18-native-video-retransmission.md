# Agent Note: 视频丢包使用原生 NACK 与 RTX 恢复

Status: implemented

## Problem

真实摄像头观看出现数秒停帧，同一时刻摄像头取流、MPP 编码和 RTP 打包仍在推进。板端 GStreamer 1.20.3 的发送 transceiver 默认 do-nack=false，实际 offer 只有 nack pli，没有通用 nack 或 RTX，不能应答视频包重传请求。
启用后实际观察到重传；但默认 100 包历史仍有请求未满足，300 秒内请求 3346 包、只发出 3205 个 RTX。该轮最大帧间隔 2.7 秒，仍未达到两秒验收线。

## Decision

发送 transceiver 在创建 offer 前启用 do-nack，由原生 webrtcbin 协商 NACK/RTX 和处理重传。Python 不自行解析生产 RTP、不实现重传线程，也不修改鉴权、摄像头参数、码率、MTU、路由或 TURN 配置。

通过已纳入会话生命周期的 deep-element-added handler，把原生 rtprtxsend 缓存固定为 1000 包。实测约每秒 160-200 包，此上限保留数秒历史；最大原始 RTP 数据约 1.2 MB/观看者，另有原生对象开销，不是无界缓存或额外播放缓冲。缓存长度不保证所有网络故障都可恢复。

关闭时先将 webrtcbin 设为 NULL，清空其重传历史，再停止整条含 MPP 编码器的管线，最后断开原生 handler。这样避免编码器先停止时仍被下游缓存引用的 DMA 视频缓冲无法归还；沿用[原生会话释放规则](2026-11-18-rtsp-session-lifetime.md)。

## Testing

新增原生合成视频回归：旧实现因 offer 缺 NACK/RTX 失败；修复后在 rtprtxsend 缓存之后故意丢一个已知序号，要求同一原始序号以 RTX 再次发出，随后继续解码十帧，并检查实际缓存上限与 RTP 1200 字节约束。不打开真实摄像头。

仅启用 RTX 时原有严格关闭回归失败，文件描述符从 18 增至 20。分类探针确认套接字稳定、RTX 原生对象已终结，但有 DMA 缓冲遗留。调整关闭顺序后严格回归通过；最终 1000 包版本十次取得实际 TURN 候选后关闭，描述符每次均为 17，Python 与原生对象终结检查通过。未放宽测试阈值。

真实流观察和完整公网验收结果记录在[部署记录](../../../deployment.md#native-video-retransmission)。可控丢包回归通过不等于真实链路流畅；不把有数秒停顿的五分钟播放标成稳定。

## Alternatives considered

- 仅靠现有 PLI 和播放器重连无需发送缓存，但不能补回丢失的视频包，且重建会话的代价更大，不能替代原生重传。
- 仅启用 NACK、保留原生 100 包默认值改动最小，但真实观察出现请求数大于发包数，因此采用有固定包数上限的更长历史；不继续无证据地增加到无界缓存。
- 修改码率、GOP、TURN 或路由可能影响传输，但当前证据首先确定的是协商缺口；本次不把这些参数混进修复，也不声称已定位全部丢包环节。

## Consequences

收益是可对协商支持 RTX 的接收端补发短时丢包，并由原生组件保持媒体边界。代价是每位观看者增加有限缓存与重传带宽；接收端未协商 RTX、长时间断网或迟到超过缓存的请求仍不能保证恢复。
本次不改变[播放器重连](../feature/2026-11-17-player-recovery.md)与[独立多观看者](../feature/2026-11-17-multiple-viewers.md)。完整公网、浏览器、长时间及容量验证必须分别说明，不能以 HTTP 健康或合成回环代替。

## Existing decision audit

检索七篇活跃记录：原生会话释放、媒体边界、播放器恢复、多人观看与本决定部分重叠，保留既有决定并互链明确重传与关闭责任。公网入口、摄像头网络、启停流程不被取代。没有完全吸收或失效提案，不删除或归档历史。
