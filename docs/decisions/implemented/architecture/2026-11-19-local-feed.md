# Agent Note: 公网观看与本机后端供流使用独立监听边界

Status: implemented

## Problem

同一块板子上的另一个服务需要接收视频，再向其网页用户分发。用户明确要求保留已有公网观看，同时新增保留 token、无需固定公网 Origin、媒体不经过云端 TURN 的本机入口。
既有 8080 同时承接 SSH 隧道，进入板子时公网请求也可能显示为回环来源；根据来源 IP 放宽鉴权会误放公网路径。只改信令地址不会解除原有 relay-only 媒体策略。

## Decision

应用在可选的 `CARSTREAM_LOCAL_PORT` 上创建独立 aiohttp 应用，只监听 `127.0.0.1`；默认 `0` 关闭，生产使用 8081，与原 8080 分离。新入口仅提供 `/ws` 与存活检查，不提供播放器或静态资源。
本机后端不发送 Origin，带任何 Origin 的 WebSocket 请求被拒绝。原 8080 精确公网 Origin 校验不变；不依据回环请求来源或转发请求头切换信任级别。云端代理与反向隧道不转发 8081。

两个入口复用同一认证与媒体生命周期实现，认证通过之后才创建独立媒体会话。令牌、认证超时、消息限制、offer/answer/ICE JSON 格式、断开释放规则均不变。
本机会话从不可变配置派生自己的设置，清空 STUN/TURN 并使用 `ice_policy=all`，不改变公网 relay 设置，也不改源、画质、重传或媒体实现。接收后端按相同的无 ICE 服务器约定使用 host 候选。
本机应用通过主应用的清理上下文启动和停止；启停脚本先检查两个端口，再确认两个端口均归新进程所有。单个本机会话断开不结束公网会话。

对方后端必须完成 WebRTC 接收，之后负责下游分发；只转发信令并不等于收流。无需提供对方网页地址。接口不是 RTSP、RTMP 或 WHEP，也不为浏览器开放任意 Origin。
完整协议、部署边界和验证方法见[本机供流接口](../../../local-feed.md)。本决定补充[Python 媒体边界](2026-11-17-python-gstreamer.md)与[公网入口](2026-11-18-public-access.md)，不取代公网 HTTP 或 TURN 决定。

## Alternatives considered

- 在 8080 上全局移除 Origin 并改成直连，接收方改动最少；但会破坏公网来源校验和当前可用的 relay-only 播放路径，因此不采用。
- 在同一监听上根据来源是回环而放行后端，配置更少；但 SSH 转发也呈现回环来源，无法形成独立可信边界，因此不采用。
- 让本机接收方继续伪造公网 Origin、使用云端 TURN，可完全不改现有应用；但把本机供流绑定到公网策略并绕云端传媒体，不满足本次明确要求。
- 新增 RTSP/RTMP 服务器便于对应生态接收；但用户目标是网页展示且已选 WebRTC，现有管线没有这两种输出，没有必要额外引入媒体服务器。

## Consequences

收益是本机后端不需要公网 Origin 或云端中继，公网观看安全策略和媒体路径独立保留。代价是新增监听与配置管理，每个本机接收者仍使用独立摄像头/硬件会话，会增加资源占用，不承诺并发容量。
回环监听不是完整的主机隔离；本机进程仍须持有 token。若人为代理或转发 8081，会破坏本机边界；Docker 隔离网络也不能直接把容器回环当作板子回环。
板端隔离的 36 项测试通过，包括来源隔离、认证先于媒体、配置不污染公网、双端口启停与会话清理。原生接收检查已解码 100 帧 2304×1296 视频，双方只交换 host 候选，ICE 服务器为空；这不是长期稳定性验收，也不声称修复旧公网停帧。
生产验证及回滚点由[部署记录](../../../deployment.md#independent-local-feed-2026-11-19)维护，不以健康接口替代真实媒体验证。

## Existing decision audit

检索活跃笔记中的 Origin、回环、TURN 与本机机制后：Python 媒体架构、公网入口和多人观看部分重叠，保留其独立会话、公网强令牌、精确来源与原生媒体边界；前两篇增加互链。
公网 HTTP、播放器恢复、低带宽、重传和启停流程未被替代；本次只补充双监听生命周期事实，不改原有决定。没有完全吸收或需要归档、否决的提案。
