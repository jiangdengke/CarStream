# Agent Note: Python 控制层与 GStreamer 媒体层的边界

Status: implemented

## Problem

需要把 RK3588 连接的摄像头画面交给浏览器，并为后续公网访问保留入口。
用户明确要求 Python，不使用 Rust，但允许调用原生媒体组件。
用户脚本提供的 RTSP 地址和凭据已通过实际打开验证，摄像头输出 H.265 Main、2304x1296、20 帧/秒。
真实场景已在浏览器出现，但持续播放仍有停帧和会话失败，不能视为直播验收通过。

## Decision

Python 使用 aiohttp 提供网页与 WebSocket 信令，通过 GI 调用 GStreamer。
RTP、ICE、DTLS/SRTP 和编码由原生组件处理，不在 Python 中逐帧搬运视频。
板端已有 MPP 编解码插件，因此 H.264 保持压缩流转发，H.265 经 MPP 解码后转为 H.264。
替换板子沿用相同媒体边界。其镜像已有 MPP 库和头文件但没有 GStreamer 插件，初次安装选择匹配 MPP 1.3.9 的插件提交 `0fc75d3710fede7ca2dfb4687362fb6979100d9e`，避免替换系统厂商库；理由与验证保存在[初次硬件插件记录](../../../deployment.md#replacement-board-hardware-plugins-and-camera-blocker)。用户随后要求新版，[独立新版运行时决定](../process/2026-11-19-isolated-latest-media-runtime.md)接管新板版本选择，不改变本篇的媒体职责边界。原本仅 root 可用的媒体设备通过专用 udev 规则只给 `linaro` 增加读写 ACL，不以 root 启动应用，也不改为所有用户可写。
编码路径显式选择 Baseline，并在 h264parse 后约束 profile。板端 MPP 默认输出 High，且原始 caps 中的 profile 使用首字母大写；解析前直接约束小写 baseline 会阻断协商。H.264 透传路径不施加这一限制。
H.264 RTP 打包上限固定为 1200 字节，为 SRTP、UDP 和 IPv6 头预留空间。默认 1400 字节包在本次热点链路上导致大量丢包，即使 ICE/DTLS 已连接，浏览器也无法组出完整帧。这里只调整应用分包，不改系统 MTU、路由或端口。

默认使用明确标识的测试画面，避免缺少摄像头凭据时阻塞服务层开发。
原首版限定一路视频、一个观看者，目的是先验证取流与浏览器链路。
单观看者限制由[取消固定观看人数上限](../feature/2026-11-17-multiple-viewers.md)部分取代；其余媒体边界保持不变。

服务端先验证访问令牌，再创建媒体会话和下发 ICE 配置。
新增的[本机后端供流入口](2026-11-19-local-feed.md)复用相同信令与媒体生命周期，但使用独立回环监听、后端无 Origin 握手和无 STUN/TURN 的会话配置；公网策略不变。
服务端发 offer，浏览器回 answer；远端描述设置前缓存 ICE 候选。
GStreamer 回调通过 asyncio 的线程安全调度投递事件，不直接写 WebSocket。
断开、超时或媒体错误会关闭当前观看会话的管线。
[摄像头 SSRC 与原生会话释放修复](../bug-fix/2026-11-18-rtsp-session-lifetime.md)明确动态视频输入和信号 handler 的清理责任，不改变原生媒体边界。
浏览器侧的[一次连接后的恢复](../feature/2026-11-17-player-recovery.md)在故障后创建新会话，不改变服务端清理当前管线的边界；播放器已部署到板子，并验证信令中断后无需再次点击即可恢复真实画面。
服务端在清理前记录已创建媒体会话的关闭摘要：完成的任务环节、原始 WebSocket 关闭码、底层异常类型、处理异常类型和持续秒数。只记录固定任务名、码和类型，不记录令牌、ICE/SDP、来源地址、关闭原因正文或异常正文。必须在主动 close() 前读取底层状态，避免清理覆盖超时证据；用户已批准诊断部署和一次受控重启，鉴权、心跳间隔及会话释放行为不变。

同步只创建新的板端发布目录，不携带密码、不自动安装依赖，也不修改网卡或启动服务。
手动后台运行使用[独立的启停脚本](../process/2026-11-17-service-scripts.md)，只管理当前发布的已核对进程，不改变同步和主机网络边界。
用户另行批准的[摄像头网口持久配置](2026-11-17-camera-network.md)属于板端部署操作，不改变应用和同步脚本不修改主机网络的边界。
公网 HTTPS 信令代理与 TURN 媒体中继是独立部署事项，不能用页面可打开替代播放验收。
[公网独立入口](2026-11-18-public-access.md)已通过私有 SSH 反向隧道和 TURN/TCP 部署，原生公网客户端完成 60 秒真实画面解码；浏览器和长期验收保持独立。

## Alternatives considered

- 厂商 SDK 能覆盖设备专有能力；但尚无可确认的 ARM64 库，也没有必要为已提供 RTSP 的设备增加专有绑定。
- Python 直接处理视频帧便于应用层加工；当前只需直播转发，逐帧路径会增加搬运和编解码成本，且无法直接复用现有 MPP 管线。
- Rust 可提供原生控制能力；用户已明确选择 Python，因此不采用 Rust 作为应用开发语言。
- 保留默认 1400 字节 RTP 包可以减少包数量；但本次跨网浏览器黑屏已复现，缩小为 1200 字节后在相同 IPv6 地址对上恢复解码，因此不依赖路径分片。没有据此新增 TURN 部署或修改网络配置。
- 当前 Rockchip 插件分支包含更新修复，但在替换板子的现有头文件上因缺少 `MppSysCfg` 编译失败；采用匹配版本，而非为安装插件替换已经存在的厂商底层库。
- 仅保留异常警告可以减少日志，但 aiohttp 心跳超时已在隔离测试复现为无原有警告的会话结束；增加无敏感内容的关闭摘要，而非打印原始信令或先修改心跳阈值。后者既缺少真实故障依据，又可能掩盖故障或暴露凭据，因此不采用。

## Consequences

收益是控制层保持 Python，且可使用板端已有硬件插件。代价是运行环境同时依赖系统 GI、GStreamer 和 Python 包，单独安装 pip 依赖不足以启动媒体会话。
替换板子的插件独立前缀和设备 ACL 需要一并维护。新版配套运行时通过 60 帧硬件 H.265 到 H.264 合成验证、27 项单测、原生 WebRTC、重传、SSRC 和清理检查；原摄像头凭据已找回并启动，实际解码 2304x1296，但一分钟连续播放检查中途结束。完整证据由新版运行时记录维护，不能将初始出画当作稳定性通过。设备规则已匹配验证，重启后权限尚未验证。
H.264 透传不能修复不被浏览器支持的编码 profile；真实 H.265 摄像头已验证可打开，并经现有 MPP 路径输出浏览器可解码画面，但持续交付仍未通过。
共享令牌仅为首版访问控制，不等同于多用户权限系统或完整公网防护。

本地和板端各 15 项配置与信令测试通过，但这些单测的媒体会话使用替身。补齐板端 GI 和 ICE 依赖后，原生 WebRTC 回环与实际服务的鉴权 WebSocket 路径均收到至少 10 个解码测试帧。原生回环还验证实际 RTP 包不超过 1200 字节，旧实现会在这一检查失败。
后续关闭诊断回归在旧实现中均因无日志失败；修改后本地 21 项 Python 测试通过、8 项 Linux 启停测试跳过，板端实际 Python 3.10/aiohttp 3.14.5 的 9 项隔离信令测试通过。Python 3.10 将异常关闭码格式化为 WSCloseCode.ABNORMAL_CLOSURE，新版 Python 格式化为 1006，两者含义相同。生产中的一次受控观看者关闭记录 1000、无底层异常并自动恢复。该诊断验证不证明此前真实断线由心跳造成；持续观察、当前进程、部署校验和回滚见[关闭诊断记录](../../../deployment.md#session-close-diagnostics-2026-11-19)。
热点下的 Cursor Chromium 浏览器已显示 640x360 彩条，解码帧数从 110 增至 308；刷新后不带诊断包装的重连也已收到 203 个解码帧。分包变小会增加相同码率下的包数量；真实摄像头、公网 TURN、其他浏览器和长期稳定性仍是验收缺口。

运行配置已按用户要求切到 RTSP/H.265，应用默认仍为测试源。真实摄像头浏览器解码从 1 帧增至 13 帧后停住，收包和丢包继续增长，之后出现媒体错误；用户截图确认出现过实际场景。
额外原生 H.264 接收端的诊断失败，单独硬件转码诊断达到至少 120 个编码缓冲后成功退出，两者都不能替代持续浏览器播放验收。
后续新建 SSH 超时，网页最终也无法重新加载，尚不能确定媒体停帧与远程连接中断是否同因。未据此改动重传、码率或网络策略，具体证据和回滚点见[摄像头源部署记录](../../../deployment.md#current-camera-source-trial)。
